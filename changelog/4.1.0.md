# Time.Tracking.Jira 4.1.0

Migration from .NET Framework 4.8 to **.NET 10 (LTS)**. For the end user this is just
another update: it installs with the same installer, over the existing installation, and
keeps the Jira connection, the tracked issues, the preferences, and any time not yet
logged. No interface changes.

Scope: 34 files — 9 new, 7 removed.

---

## Why

.NET Framework 4.8 doesn't receive new features and ties the application to APIs Microsoft
has already retired. .NET 10 is LTS with support until November 2028. .NET 8, the initial
target, was dropped because its support ends in November 2026 and would force repeating
the migration soon after.

## How it affects an existing installation

**It updates in place; there's no need to uninstall or reinstall.** The installation's
identity is the installer's `AppId`, which has no relation to the .NET version and didn't
change. The installer still finds the previous installation, reuses its folder and its
shortcuts, closes the running instance, and replaces the files.

**New requirement: .NET Desktop Runtime 10 (64-bit).** Previously .NET Framework 4.8, which
ships with Windows, was enough. Now the installer checks whether the runtime is present
and, if it's missing, offers to download and install it on the spot (~60 MB); in unattended
mode (`/VERYSILENT`) it does so without asking. The installer itself still weighs ~3 MB.

**Higher minimum requirements:** 64-bit Windows 10 version 1607 (or Server 2016). .NET 10
doesn't support Windows 7, 8.1, or 32-bit Windows. A machine in that situation can't
receive this update and must stay on 4.0.5.

## Where the configuration lives now

It moves to its own file:

```
%LOCALAPPDATA%\Seabury Solutions\Time.Tracking.Jira\settings.json
```

Previously this was handled by `System.Configuration`, which saved it in a `user.config`
inside a folder whose name .NET computed from the executable and its version
(`Time.Tracking.Jira.exe_Url_<hash>\<version>`). That name stopped being reproducible after
the migration, because the managed assembly was renamed to `Time.Tracking.Jira.dll` and the
`.exe` is now a native launcher: both the folder name and the hash change.

Because of this, **on first launch after updating the application imports the previous
installation's configuration on its own**: it looks for the most recently written
`user.config` — the one from the version the user actually used last, which isn't always
the one with the highest number — and converts it. This includes the password, which is
copied as-is, encrypted with DPAPI, without ever passing through plain text.

The previous `user.config` **is neither deleted nor modified**. This is deliberate: it
allows rolling back to 4.0.5 if needed, and that version finds its configuration intact.

The log file (`jirastopwatch.log`) moves to that same folder. It used to go to a path that
included the product version, so it started a new folder — and lost its history — on every
release.

## Fixed

- **The system tray icon would have disappeared.** It was extracted from the running
  assembly, which under .NET Framework was the `.exe` itself. Under .NET the assembly is a
  `.dll` with no icon resources; it's now taken from the executable explicitly. The same
  applies to the version shown in the "About" window and the one the installer reads.

## Technical note

- The projects move to SDK-style format and from `packages.config` to `PackageReference`.
  The application's `.csproj` drops from ~300 lines to ~55.
- **`BinaryFormatter`**, which stored the grid rows, doesn't exist in .NET 10. Rows are now
  stored as JSON. Data already written is still read with `System.Formats.Nrbf`, a
  read-only decoder for that same binary format included in
  `Microsoft.WindowsDesktop.App`: it decodes without constructing any object, so it also
  doesn't carry the security issue `BinaryFormatter` was retired for. The same applies to
  the import from the original "Jira StopWatch", which no longer needs the assembly-name
  remapping it used to require.
- **RestSharp stays at 106.12.0**, which targets `netstandard2.0` and works as-is on
  .NET 10. Upgrading to 11.x breaks the API completely (`IRestClient` and `IRestRequest`
  disappear) and would require rewriting the entire Jira layer: left for a separate change.
- The reference to **Newtonsoft.Json** is removed — it was declared but unused anywhere —
  along with `System.Web`, in the same situation.
- `PersistedIssue` is removed, a type that existed only so `BinaryFormatter` could
  reconstruct it, along with the `App.config` and its entire `userSettings` section.
- The dead `CheckForUpdate` setting is removed — it was saved and read back without
  anything consulting it since the update check was removed in 4.0.5.
- The application is now explicitly declared Windows-only (`SupportedOSPlatform`), which is
  what lets the platform-compatibility analyzer skip flagging every call to WinForms, WPF,
  GDI+, and DPAPI. The build is now warning-free.

## Tests

The full suite was redone: from 39 cases with 6 failing to **68 passing**.

- The Jira layer tests were outdated and had been failing since before this migration,
  against code that had changed without them being updated: they still expected the
  search API v2 (now v3) and a login via POST with username and password in the body,
  when authentication had long since moved to a `Basic` header on every call. They were
  rewritten against current behavior, and the missing cases were added (issue
  autocomplete, time-tracking configuration, and the four remaining-estimate adjustment
  modes when logging a worklog).
- Worklog body comparisons were done via `GetHashCode()` on anonymous types, which doesn't
  say which field differs when it fails; fields are now compared directly.
- `JiraClientTest` no longer leaves the global time-tracking configuration contaminated,
  which made the result depend on execution order.
- New migration tests, using a real `user.config` from a 4.0.5 installation as a fixture:
  they cover every setting, the grid rows with their exact time, choosing the source among
  several installation paths, and making sure a corrupt or unreadable file doesn't prevent
  startup.
- Upgraded to NUnit 4 and Moq 4.20 (previously NUnit 2.6.4 and Moq 4.2, from 2015, which
  don't build on .NET 10).

## Still to verify

- The running application was not tested on .NET 10: neither the window startup, nor the
  tray icon, nor the remaining WinForms dialogs (`EditTimeForm`, `FocusWidgetForm`).
- The installer was not tested against a real 4.0.x installation, nor the runtime download
  on a machine that doesn't have it.
- **Screen scaling:** WPF moves from "System DPI aware" to "Per-Monitor v2", the default in
  modern .NET. On a single monitor it shouldn't be noticeable; with several monitors at
  different scales, rendering changes. If this becomes a problem, it can be pinned with
  `<ApplicationHighDpiMode>SystemAware</ApplicationHighDpiMode>`.
- The import from the original "Jira StopWatch" was only tested with a file whose rows
  were all empty: discarding empty rows is covered, and recovering a row with data shares
  the decoder with the grid (which is covered), but has no test of its own.
