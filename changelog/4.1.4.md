# Time.Tracking.Jira 4.1.4

**The application stopped using RestSharp**, the library it had always used to talk to
Jira. The version it shipped dated back to 2021 and had gone five years without security
patches. Calls to Jira now use `HttpClient`, which ships with .NET.

**For anyone using the application, nothing should change.** Connecting, searching for
issues, fetching subtasks, and logging work all behave the same as in 4.1.3. That's
exactly the point: this is a plumbing change, not a behavior change.

Scope: 25 files — 4 new, 4 removed.

---

## Why

RestSharp 106.12.0 was published in 2021, targeted `netstandard2.0`, and internally used
`HttpWebRequest`, .NET's old HTTP stack. It still ran fine on .NET 10, but:

- **Five years without security updates.** Everything the application sends to Jira —
  including the username and API token — went through it.
- None of what .NET has modernized since then in TLS, proxies, and connection handling.
- Upgrading to RestSharp 11 wasn't an option: it changes its entire API and would have
  required rewriting the Jira layer anyway. If it had to be rewritten, better to do it
  without the dependency.

**The installer gets smaller**: the application no longer ships any third-party library,
it's a single executable.

## What to look at if something breaks

The change is plumbing, but it's the plumbing everything runs through. If something looks
off, it's almost certainly in one of these three:

- **Connecting to Jira.** Authentication and the session cookie are now handled by
  `HttpClient`. If the session drops and reconnects on its own, that path is new.
- **Searching for issues.** Search by key and Jira's autocomplete build their URLs with new
  code.
- **Logging work.** The worklog body and the estimate-adjustment parameters are serialized
  with a different library.

The log still records every request and every response just as before, so if something
fails, the log will show it.

## Technical note

- New `Http/`: `JiraRequest` (with `IJiraRequest` and `IJiraRequestFactory`),
  `JiraResponse`, and `JiraHttpClient` (with `IJiraHttpClientFactory`). **The same shape**
  the RestSharp wrappers had was kept — a request factory and a client factory — so
  `JiraApiRequestFactory`, `JiraApiRequester`, and `JiraClient` change types but not logic:
  the retry on 401/400, the 2xx check, and the special-cased 410 Gone are the same as
  before.
- `JiraHttpClient` **blocks on purpose**. Every call already runs on a background task and
  the rest of the application is synchronous, so waiting here confines the change to the
  transport instead of spreading `async` through every call site.
- The `CookieContainer` lives on the handler, so invalidating cookies on reauthentication
  means a new `HttpClient`. That's what `JiraHttpClientFactory.Create(true)` does.
- **The DTOs lost their duplicate property pairs.** Every field had two properties over the
  same backing field (`key` and `Key`) because RestSharp's deserializer matched by exact
  name. `System.Text.Json`, configured case-insensitive, treats that as a duplicate and
  refuses to bind, so each field is now down to a single property: 279 lines down to 190.
- `JiraResponse.Content` is never null. RestSharp guaranteed the same, and
  `ReAuthenticate` assumed it: a response with no body would have made it fail.
- `source/StopWatch/RestSharp/` and the package reference are removed. The application has
  no NuGet dependency at runtime anymore.
- The suite goes from 136 to 148 tests. The 12 new ones cover the transport: how the URL is
  built — including the case of a resource that already carries its own query string — and
  that the camelCase JSON Jira returns still binds to the DTOs now that another library
  reads it.

## Still to verify

- **None of this was tested against a real Jira instance.** The tests reach up to the edge
  of HTTP: they verify the URL, the headers, and the JSON, but none of them opens an actual
  connection. Still need to test against production Jira: connecting, searching by key,
  searching by text, fetching a parent's subtasks, and logging a worklog with an estimate
  adjustment.
- **Reauthentication is the least-covered path.** There are tests confirming it retries on
  401 and 400, but with the transport simulated. Still need to see a real dropped session
  recover on its own against Jira.
- Not tested behind a corporate proxy. `HttpClient` picks up the system's proxy
  configuration by default, same as RestSharp did, but this hasn't been verified.
- The installer was built, not installed. Still need to run `Build-Installer.ps1` and
  confirm the package without `RestSharp.dll` installs and starts.
