# Time.Tracking.Jira 4.0.3

Import of settings from the original app this project forked from — "Jira StopWatch",
normally installed at `C:\Program Files (x86)\Carsten Gehling\Jira StopWatch`.

Scope: 6 files — 1 new.

---

## Import from Jira StopWatch (legacy)

New link in Settings, next to the connection section: **"Import from Jira StopWatch
(legacy)…"**.

Brings over, in one shot:

- **Connection**: Jira URL, username, and API token.
- **General and behavior options**: the same ones we already have, with the sole
  exception of the startup view, which didn't exist in the original app.
- **Issues with unlogged time in Jira.** These are added as new rows to the Ledger (and
  therefore also visible in Cards, Focus, and Grid), always paused — even if they were
  running in the old app — so they can be reviewed before resuming anything. Their titles
  are resolved automatically against Jira as they're added, just like any new row.

The app looks for the settings on its own: there's no need to point it to where the old
app is installed. If it can't find it, it offers to pick the file manually.

Nothing is applied until the Settings dialog is accepted — cancelling discards the whole
import, fields and issues alike, just like it discards any other change made in the
dialog.

### Verified with real data

Against a real installation of the original app on this machine: it found the settings on
its own, decoded username, URL, and token, and recovered 4 issues with unlogged time
(5h 17m total) with their data intact — including each one's real start time, which is
what Jira needs to date the worklog correctly.

---

## Technical note

The old app's unlogged issues are serialized under the exact identity of its own assembly
(`StopWatch, version 2.x`), different from this project's (`Time.Tracking.Jira, version
4.x`) even though the classes are the same. The import redirects that identity when
reading them, without touching the format of our own saved data.
