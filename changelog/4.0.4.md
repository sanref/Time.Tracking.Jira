# Time.Tracking.Jira 4.0.4

Search box inside the issue combo boxes: typing filters the list by code, and anything not
in the list is searched for in Jira.

Scope: 9 files — 2 new.

---

## Search by typing, by issue code

The four issue combo boxes — **Parent issue** and **Subtask**, both in the *Add issue*
dialog and when editing a Ledger row with a double-click — filter the list as you type:

- Matches **anywhere in the code**, not just at the start: `6573` finds `ALK-6573`, and
  `T-698` finds `EAUT-698`.
- **Several words** separated by a space must all match: `alk 65` keeps only the ones that
  satisfy both.
- Case-insensitive.

It searches **only by code**, not by title. The title still shows below each code in the
list, as context.

The list opens on its own as you type and closes if nothing matches. Once an item is
chosen — or when leaving the field — the filter is discarded, so opening the list again
with the arrow offers it in full once more.

This replaces WPF's built-in search, which only jumped to the code that *started with*
what was typed. With the *Parent issue* list, which brings in every issue assigned to the
user, that search was useless: either you knew the exact code by heart, or you had to
scroll down the list by hand.

## Parent issue search reaches all of Jira

The *Parent issue* combo box loads with **the issues assigned to the user and not
closed**, which is what it offers before anything is typed. The search, however, is no
longer limited to those: every time you type (from 3 characters on) Jira is also queried,
whether or not there are matches in the loaded list.

- A **full code** — `ALK-6573` — is requested by code: it shows up regardless of assignee,
  whether it's closed or not, and from any project.
- A **partial code** — `6573`, `ALK-65` — goes to Jira's own autocomplete, the only thing
  that knows how to match half a key; JQL can't.
- Whatever Jira returns, only what **matches the searched code** is kept: Jira's
  autocomplete also answers by title, and issues that had nothing to do with what was
  typed used to sneak into the list.

What's found is added to the combo box's list, with its title already resolved, and stays
there for the rest of the session — even if the assigned-issues list is reloaded with
*Refresh*.

The query waits for typing to pause (0.35s) and isn't repeated for text that was already
searched, so typing a full code in one go is **one** query, not one per letter. Without a
connection to Jira, the combo box falls back to its local search.

## Fixed

- **The first character was eaten by the second.** When the list opened, WPF selected the
  entire text in the field — as if it had been highlighted with the mouse — so the next
  letter replaced it instead of continuing it: typing `AL` left `L`. The cursor now stays
  where the keyboard left it, with nothing selected.
- **Issues that didn't match the search were showing up.** The first search showed
  nothing and, on reopening the combo box, the list brought in issues unrelated to the
  text: they were the ones Jira had returned by title. These are now discarded on
  arrival.
