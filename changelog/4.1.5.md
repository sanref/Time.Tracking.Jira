# Time.Tracking.Jira 4.1.5

**"Log all" is now a single dialog**: every row with time listed together, each with its
own comment, logged all at once. **The Jira connection now recovers on its own** if the
application started without network or VPN. And five fixes:

- **a failed log entry says why**;
- **locking the session pauses every timer**, and resumes every one of them;
- **unlocking also resumes an issue-less row**;
- **a corrupted settings.json is no longer lost**;
- **an already-logged comment no longer reappears** the next time.

Scope: 25 files — 7 new.

---

## Log all in a single dialog

Before, *Log all* opened the logging dialog once per row, one after another, and silently
skipped rows without an issue. Now it opens a single window:

- **Every row with time listed together**, in the same order as the main window. Each one
  shows its issue, its time, and the start time it's about to be logged with.
- **Each row has its own comment.** If a row had one parked with *Save for later*, it
  shows up already written.
- **You choose what to log** with each row's checkbox. At the top you can see how many are
  going and how much time they add up to. By default, all of them are selected.
- **Rows without an issue show up disabled**, with the reason. Before, they were skipped
  without any indication.
- **A single button, *Log selected*** (or Ctrl+Enter), and each row shows how it went:
  *Logged ✓*, or the reason Jira gave if it didn't accept it.
- **The window stays open with the results.** A row that failed stays marked: it can be
  fixed and resubmitted. It can't be closed while sending.
- **Nothing you wrote is lost:** the comment on a row that wasn't logged stays on the row
  for next time.

What this dialog **doesn't** let you edit is the start time and the remaining estimate:
each row uses its own. The estimate is the automatic one, unless a different one was
parked with *Save for later*, in which case the row indicates it. Row-by-row logging is
still there, unchanged, for changing those.

A row that was running is left paused after being logged, same as with individual
logging.

## The Jira connection now recovers on its own

If the application starts without network, without VPN, or with Jira down, it no longer
gets stuck on *Not connected* until someone clicks the button:

- The status reads **Offline** and the application **keeps retrying on its own**: at 15
  seconds, at 30, at one minute, at two minutes, and every 5 minutes from there on.
- **When the network changes** — Wi-Fi connects, the cable is plugged in, or the VPN comes
  up — the retry is moved up and happens within a few seconds.
- Clicking the status still reconnects immediately, as before.
- **A rejected user or token is not retried.** Repeating failed logins against Atlassian
  can end in a CAPTCHA or a locked account. That case still says *Not connected* and waits
  for it to be fixed in Settings.

If the network drops while the application is already connected, there's no need to
reconnect: every call to Jira carries its own credentials, so it works again on its own
once the network is back.

## Fixed

**A failed log entry now says why.** When Jira rejected a worklog, the warning said
*"Error posting worklog for X:"* and nothing else: the reason was lost along the way. It
now shows what Jira responded, for example *"Issue does not exist or you do not have
permission to see it."* or *"You do not have the permission to associate a worklog to this
issue."*. This also applies to each row's result in *Log all* and to what ends up in the
log.

**Locking the session pauses every timer, not just the first one.** With *Allow multiple
timers* enabled, locking the computer only paused one of them, and the rest kept adding up
the locked time. Now all of them are paused and, with *Pause and resume*, all of them
resume on unlock.

**Unlocking also resumes an issue-less row.** A timer started before choosing an issue —
something v4 deliberately allows — stayed paused after unlocking, even though the setting
said *Pause and resume*. And with two rows on the same issue, the wrong one could end up
resuming. Now exactly the row that was paused resumes.

**A corrupted settings.json is no longer lost.** If the settings file couldn't be read,
the application started with default values and the autosave would overwrite it within a
minute: the Jira connection and all unlogged time were lost. Now, before continuing, it
saves a copy next to the original (`settings.json.corrupt-<date>`), and a startup warning
says where it ended up. The unlogged time is in that copy.

**An already-logged comment no longer reappears.** After logging a row with a comment,
the next time that same row was logged the dialog opened with the previous comment
already written, as if it were still parked, with the same estimate option too. v3 used
to clear these on logging; that behavior is restored now. If the log attempt fails, the
comment is still kept for the next try, same as before.

## Technical note

- **Error reason.** `JiraErrorText` reads the body of a rejected response
  (`errorMessages`, `errors`, `message`), and `JiraHttpClient` builds the message from it:
  *"<Jira's text> (HTTP 403)"*. If the body carries nothing, it falls back to the status
  line, as before.
- **Why the warning came out empty.** `JiraClient.PostWorklog` didn't copy the reason, and
  on top of that the reason was read after the call, from the requester's shared state,
  which every background task uses at once. Now `RequestDeniedException` carries the
  reason and an `Unreachable` flag (Jira didn't respond, or responded with 5xx or 429).
  `PostWorklog` returns the error through an `out` parameter.
- **Reconnection.** `SessionState.Unreachable` is the only connection outcome that gets
  retried.
  - `JiraSession.Connect` is serialized: two simultaneous connections (the one at startup
    and the one from an accepted Settings dialog) were writing over the same client.
  - It listens for `NetworkChange.NetworkAddressChanged` and `NetworkAvailabilityChanged`.
  - If a response from an old attempt arrives after a new one has already started, it's
    discarded.
- **Timer accounting.** What happens to the timer after a successful log entry
  (`SettlePosted`) doesn't change; it's now shared between individual logging and *Log
  all*.
- **Session lock.** The pause stores the rows, not the issue key: a row without an issue
  has an empty key, and two rows can share the same one.
- **Tests: from 148 to 206.** The new ones cover:
  - reading Jira's error responses,
  - when a failure means Jira didn't respond,
  - locking with several rows,
  - the timer and the draft comment after a log entry,
  - the corrupted settings.json copy,
  - the *Log all* dialog, with a test that opens it off-screen in every state,
  - the wait between retries.
- **Window tests.** They now pin `ShutdownMode.OnExplicitShutdown`. With a single window
  per fixture this wasn't needed; with two, the WPF application used to close along with
  the first one.

## Still to verify

**None of this was tested against a real Jira instance or with the application actually
running.** It was compiled, the tests passed, and the *Log all* window was rendered
off-screen for a visual check. Still missing:

- **Log all:**
  1. Set up three rows: one without an issue and one running.
  2. Log them and check each row's result.
  3. Confirm the one that was running ends up paused.
  4. Confirm a row that fails keeps its comment on close.
- **Error reason:** log against a key that doesn't exist and see Jira's text in the
  warning.
- **Reconnection:**
  - Open the application without network or VPN. It should say *Offline*.
  - Connect the network afterward. It should switch to *Connected* on its own within a
    few seconds.
  - With a wrong token: *Not connected* and no retry in the log.
- **Session lock:**
  1. Enable *Allow multiple timers* and start two rows, one of them without an issue.
  2. Lock with Win+L for a minute and unlock.
  3. Both should still be running, without having added the locked minute.
- **Corrupted settings.json:** with the application closed, corrupt the file and open it.
  A warning with the copy's path should appear, and the copy should have the original
  content.
